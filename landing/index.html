Noetrix

It cites every claim[1]
and admits every gap.

Point it at a folder. Notes, PDFs, scanned books, notebooks, source code. Ask a question and get an answer built only from what it actually retrieved, with a marker on each claim that resolves to the passage it came from.

The second half is the hard half. When your documents do not cover something, it says so, rather than producing the most plausible sentence it can.

The problem

A chatbot has never read your files.

It cannot tell you what your handbook actually requires, how your codebase solved a problem last year, or which page of your reference carries the proof. So it does the worst possible thing: it produces something plausible.

This indexes a document collection and answers strictly from it. The citation isn't decoration, it's the contract. Every marker resolves to a chunk that was actually retrieved, and a second pass can check that the sentence is genuinely supported by the source it points at.

It reads Markdown (wikilinks and YAML frontmatter included), PDFs (scanned ones too, through OCR), Jupyter and R notebooks, source code in most languages, and Office documents. A directory of files is enough.

The pipeline

Six stages, each one swappable.

Nothing here is a wrapper around an embedding call. Every stage is configured from one file, and the optional lanes open only when a query calls for them.

Pick a stage to see what it does to the query. These are the same six steps the trace at the top runs through.

What makes
it good

The parts that took the longest.

Soft scope routing can't empty your results

Scoped chunks get guaranteed seats in the candidate pool, but the reranker still makes the final call. A hint that turns out to be wrong degrades gracefully instead of returning nothing, which is what hard metadata filters do on the day you need them most.

A dedicated code lane or code never surfaces

Code is usually a small slice of a corpus, so a prose-oriented pipeline buries a real function under pages that merely mention its name. Detecting code intent, skipping expansion, widening the pool and reserving a filtered lane brings the actual implementation back to the top.

Reranking you choose bigger isn't better by default

The cross-encoder is swappable, can run on a GPU or out-of-process behind an HTTP endpoint, and can be replaced by a model-free lexical scorer on hardware that can't afford one. A larger model that scores higher on public benchmarks can still cost many times the latency for no measurable gain on your corpus, which is what the evaluation suite is there to settle.

Three OCR lanes scanned pages aren't one problem

Tesseract is built in and free. PaddleOCR runs as its own container, far stronger on skewed, multi-column and non-Latin scans and still seconds per page on a CPU, and it stops when you're not ingesting. A document vision model handles the hardest material over HTTP. A page scanner tells you which pages actually need any of it.

Failures that name themselves no silent fallbacks

A generation outage returns a readable error, not a 500, and retrieval keeps working. A reranker error is reported as a retrieval failure, not misfiled as a provider problem. And if the pipeline can't be built at all, the health endpoint says so with the reason instead of leaving you to watch a spinner.

Evidence

Measured, and honest about the measurement.

A labelled suite scored in three tiers. Every metric reports how many questions it was actually scored over. A metric with no ground truth reports not scored, never a confident zero.

TierWhat it measuresNeeds
1 · Retrieval hit-rate@k, MRR, recall@k over expected source files, scope precision and recall nothing but the index; runs offline in minutes
2 · Answer keyword recall, citation validity, the groundedness floor, citation support a generation endpoint
3 · Calibration correctness bucketed by the answer's own confidence line, and the HIGH−LOW gap a generation endpoint

The groundedness floor

The part worth defending, because it's deterministic and needs no language model. For each cited sentence it measures content-word overlap with the chunk that sentence points at, and names the worst-scoring sentence. High overlap doesn't prove a claim is right, but but low overlap means a sentence barely resembles the source it cites, which is the exact shape of a fabricated citation. It also catches a [9] pointing into a seven-source context, which generators otherwise drop in silence.

An LLM-as-judge tier exists and is labelled advisory: a model grading a model is useful for ranking two runs against each other, not as ground truth. Where a question has no reference answer, the judge's score is discarded rather than recorded.

For agents

Every capability is an HTTP call.

Nothing requires the browser interface: the management console is itself just a client of its own API. Both services publish a live schema, so an agent discovers what it may call instead of carrying a hard-coded list that quietly goes stale.

The primary agent call: retrieval only, no tokens spent
# ask what this install actually supports, then ground a question
curl -s http://127.0.0.1:8051/schema

curl -s -X POST http://127.0.0.1:8051/search \
  -H "Content-Type: application/json" \
  -d '{"q": "how do we rotate service credentials",
       "top_k": 6, "include_text": 1200}'

# every source carries a stable id you can dereference
curl -s http://127.0.0.1:8051/chunks/<id>?include_text=4000

Search, don't generate by default

Retrieval runs locally and needs no generation backend at all. An agent that can already reason wants the raw passage, not a paraphrase of it, so paying for a generation pass to summarise chunks it will re-read anyway is double spend.

Permission tiers on every operation read / mutating / destructive

The management API labels each of its operations so a toolkit can gate them: read freely, confirm before mutating, and always echo exactly what will be removed before removing it.

Comparison trees one call, several branches

Run one question under several presets, rerank methods or generation backends and get shared and unique evidence, rank shifts and pairwise overlap back. Branches differing only by backend reuse identical evidence, so the comparison is about the answer rather than retrieval noise.

Run it

Two ways in.

Free and local by default: CPU embeddings, on-disk indexes, no managed service. Generation is the only part that can be remote, and retrieval works without it.

Everything, in two commands
# query API :8051 · console :8052 · generation :3001
docker compose up --build -d

# heavy extras are opt-in, and stoppable when idle
docker compose --profile ocr    up -d --build paddleocr
docker compose --profile rerank up -d rerank
docker compose stop paddleocr   # give the memory back

The container image installs CPU-only PyTorch first, so it never pulls multi-gigabyte GPU wheels. Indexes are mounted, not baked in.

Python 3.11: index, then ask
pip install -r requirements.txt
cp config.example.yaml config.yaml   # point it at your documents

python -m src.ingestion.obsidian_parser "path/to/docs" -o data/chunks.jsonl
python main.py index

python main.py query "What does our incident response process require?"
python main.py eval --retrieval-only   # offline regression, minutes

PDFs, notebooks and source code each get their own ingest pass and append into the same index.
